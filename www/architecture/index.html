Документация Harness

Архитектура Harness

Почему требования, решения, задачи, реализация и доказательства разделены — и как они образуют одну traceable систему.

Три слоя, три разных ответственности

HARNESS / PROTOCOL
AGENTS + skills + commands + policies
             ↓
PROJECT KNOWLEDGE BASE
PROJECT + REQ + ADR + architecture + planning
             ↓
IMPLEMENTATION
code + tests + migrations + runtime config

Harness — process layer, а не application framework. Product implementation folders намеренно отсутствуют из template до INIT и реальных STEP.

REQ, ADR и STEP не смешиваются

REQ

Что система обязана обеспечивать? Canonical source — docs/requirements/SPEC.md.

ADR

Какое устойчивое архитектурное решение принято и почему? Canonical source — docs/adr/.

STEP

Какую ограниченную работу выполняем сейчас? Canonical source — planning/tasks/STEP-NNN.md.

Evidence

Какими реальными проверками и артефактами доказан результат acceptance criteria?

Canonical sources и projections

STEP-NNN.md — canonical task contract. PLAN.md и STATUS.md — удобные projections. Если projection расходится с task/evidence/factual state, projection исправляется, а не становится новой истиной.

Иерархия источников истины

  1. Фактический code / migrations / config / tests.
  2. Accepted ADR.
  3. Architecture/subsystem docs.
  4. Requirements.
  5. STEP.
  6. PLAN/STATUS projections.
  7. Brief, chat и неформальные заметки.
Code не объявляется автоматически «правым». Если он расходится с Accepted ADR, это architecture drift, который нужно явно разрешить.

Роли и независимый контроль

Reasoning-heavy стадии можно отдавать сильным planner/reviewer профилям, а механическую реализацию — более экономичному implementer. Reviewer остаётся независимым от implementer. Model/effort настраиваются в .codex/agents/*.toml.

Technology knowledge подключается on demand

Harness не вшивает все framework playbook в template. FIND SKILL ищет capability, пользователь выбирает кандидат, INSTALL SKILL фиксирует provenance и routing. Third-party skill никогда не становится выше repository contract.
