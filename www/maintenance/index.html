Поддержка и обновление

Как изменять живой проект без процессного долга: короткий путь для мелких правок, явное восстановление согласованности и безопасное обновление служебного слоя Harness.

Служебный слой Harness и код проекта обновляются по-разному

К Harness относятся AGENTS, адаптеры сред исполнения, базовые навыки, протокол выполнения, .harness/docs, политики, механизм обновления, валидатор и шаблоны. Проекту принадлежат REQ, ADR, архитектура, задачи, ревью, аудиты, код и тесты продукта, конфигурация и дополнительные навыки проекта или сторонних источников.

Для мелкой правки не нужен искусственный STEP

Опечатка, пунктуация, безопасный комментарий или локальное форматирование могут идти через PROJECT QUICK FIX или ручную правку. изменения Git и коммит — достаточная история такой мелочи.

Короткий путь запрещён при изменении поведения, API, схемы или миграций, аутентификации и безопасности, зависимостей, архитектурных границ, существенной стратегии тестирования либо требований и критериев приёмки.

PROJECT RECONCILE восстанавливает согласованность

Расхождения архитектуры, документации и статусов фиксируются явно. PROJECT RECONCILE создаёт отчёт аудита и корректирующий STEP там, где изменение нельзя безопасно спрятать в текущую задачу.

Прямая установка конечного релиза

HARNESS UPDATE CHECK [TO <tag>]
HARNESS UPDATE APPLY [TO <tag>]

Диспетчер направляет команды в .harness/tools/harness-update.py без вызова модели. CHECK ничего не записывает; APPLY повторяет свежую проверку перед первой записью.

Обновление выполняется напрямую к конечному релизу за одну транзакцию, без промежуточных APPLY. .harness/harness.lock.json фиксирует установленный BASE; без TO из .harness/harness-update-graph.json читается только latest. Явный TO <tag> выбирает неизменяемый релиз без чтения каталога. Новый механизм не строит маршрут по transitions.

BASE — установленный неизменяемый релиз, OURS — локальные служебные файлы, THEIRS — конечный релиз. Журнал .harness/local/update-journal/ сохраняет байты, права, файл состояния и состояние выполнения. Установка проверяет служебные файлы, синтаксис и конфигурацию; не запускает код целевого релиза, полный валидатор проекта, хуки или начальную настройку целевого релиза. После PASS публикуется один отчёт, затем атомарно фиксируется транзакция. Сбой до момента фиксации откатывает изменения.

При оставшемся журнале CHECK возвращает UPDATE_JOURNAL_PENDING. Следующий APPLY сначала восстанавливает состояние; для диагностики доступен python3 .harness/tools/harness-update.py recover --json. UPDATED означает достижение целевого релиза. Если reloadRequired=true, перезапустите среду перед работой; повторный APPLY вернёт NO_UPDATE, а не продолжит цепочку промежуточных установок.

Установка меняет служебный слой Harness и файл состояния. Код, REQ/ADR/STEP, REVIEW, доказательства и проектные шаблоны сохраняются как есть: их повреждение или устаревание не блокирует установку. Успешное обновление не означает миграцию продуктовых данных, приёмку STEP или успешную проверку проекта. PROJECT RECONCILE выполняется отдельно, когда требуется миграция проектных документов.

После установки изучите изменения и выполните GIT CHECK. Обновление не создаёт коммит, push или PR.

BASE / OURS / THEIRS и правила владения файлами

harness_owned

Локальное отличие от BASE блокирует скрытую перезапись.

shared

Для настраиваемых файлов выполняется трёхстороннее слияние. Сюда входят отслеживаемые файлы ролей и конфигурации Codex и Claude Code.

marker_merge

README и AGENTS объединяются с сохранением сгенерированных блоков проекта.

unknown

По умолчанию файл считается принадлежащим проекту, и механизм обновления его не меняет.

Схема проектных документов мигрируется отдельно и без скрытой потери данных

HARNESS UPDATE APPLY обновляет служебный слой, но не переписывает активные проектные REQ/ADR/OQ/STEP. Если целевой релиз требует миграции, валидатор оставляет явное состояние ожидания; затем PROJECT RECONCILE сначала без изменений выполняет предварительную проверку всех заранее обнаружимых блокирующих проблем и только после этого изменяет проектные документы и пересобирает проекции.

Миграция устаревших документов сохраняет неизвестные разделы и исходные метаданные, многострочные зависимости, русский формат ADR и свободный текст старого монолитного SPEC. Написанные вручную файлы на месте генерируемых проекций перед заменой сохраняются рядом как *.legacy.md. Завершённые старые STEP без доверенного исторического ревью могут получить явный LEGACY_COMPLETION исходное состояние в отчёте миграции — это совместимость с историей, а не поддельный PASS-отчёт задним числом.

Неизменяемые исторические отчёты не переписываются; уже зафиксированные подтверждения ревью проверяются по хэшам, а повторная миграция без изменений остаётся идемпотентной.

Совместимость старых установок

Старый уже установленный механизм обновления может блокировать обновление по STEP/REVIEW/STATUS до получения новых файлов. В таком случае официальный протокол обновления описывает явный запуск установщика из отдельного checkout выбранного неизменяемого релиза с --root целевого проекта. Не редактируйте файл состояния и не копируйте служебные файлы вручную.

При отсутствии файла состояния подключение через adopt --from vX.Y.Z требует известной неизменяемой основы. Исторические снимки v0.6.0 и v0.7.0 имеют две документированные ошибочные пары релиза и OID: только для них предусмотрено точечное восстановление. Любой другой SOURCE_TAG_MOVED остаётся блокирующей ошибкой доверия к источнику.

Изменяющие операции Git тоже проходят детерминированные границы безопасности

Перед GIT CHECK, GIT COMMIT, GIT PUSH, GIT PR, GIT PR FINISH и GIT SYNC используется .harness/tools/git-preflight.py. Он возвращает PASS/BLOCKED и точный план операции; фактические механические изменения выполняет .harness/tools/git-action.py, а операции Pull Request с учётом особенностей сервиса — .harness/tools/pr_provider.py.

Для GIT COMMIT до валидатора фиксируются ветка, HEAD и дерево индекса. Перед git commit снимок проверяется повторно, а после него сверяются фактические ветка/родитель/дерево. Пользовательские хуки не отключаются. Если хук изменил проверенное состояние, результат становится COMMIT_POSTCONDITION_FAILED; Harness компенсирует только доказанно принадлежащее операции изменение ссылки через reflog и compare-and-swap. Неоднозначная ситуация блокируется, а git reset --hard для восстановление не используется.

COMMIT/PUSH/PR также сохраняют ограниченную контрольную запись внешней операции в состоянии выполнения. После сбоя Harness сначала наблюдает внешний факт: уже доказанное изменение не повторяется, неизменившееся исходное состояние допускает повторную попытку, а третье состояние возвращает SIDE_EFFECT_RECOVERY_AMBIGUOUS. Для отправки проверяется фактический HEAD удалённой ветки; для PR выполняется точный запрос к сервису по исходной и целевой веткам и SHA исходного коммита.

Для GIT PR FINISH предварительная проверка подтверждает, что PR уже имеет состояние MERGED, рабочее дерево чистое, локальный HEAD соответствует сохранённому в сервисе SHA исходного коммита, а ветку возврата можно безопасно обновить fast-forward. Локальный .harness/local/git/pr-state.json удаляется только после полностью успешного завершения.

Работа с сервисом PR — отдельная возможность. GitHub использует gh, Gitea — tea. Для собственного сервера Gitea адрес берётся из настроенного push.remote; несколько подходящих профилей tea дают PROVIDER_LOGIN_AMBIGUOUS. GIT CHECK, GIT COMMIT, GIT PUSH и GIT SYNC используют обычный Git.

Доверие к источнику и границы установки

Из изменяемой исходной ветки читается только каталог для выбора latest; с явным TO каталог не нужен. Устанавливаемые файлы берутся из неизменяемых тегов релиза. SOURCE_TAG_MOVED, CURRENT_RELEASE_DRIFT, конфликт слияния, небезопасный путь и повреждение служебной конфигурации блокируют установку.

Проектные документы не являются проверками установки. Полноту приёмки, актуальность доказательств и схему рабочих артефактов проверяют соответствующие команды проекта.

Временные файлы и безопасная очистка

Рабочие снимки, вспомогательные скрипты и промежуточные логи кладите в temporaryDirectory из документа передачи: .harness/local/tmp/<executionId>/. Доказательства, неизменяемые REVIEW и данные восстановления хранятся у своих владельцев вне tmp.

HARNESS CLEANUP CHECK только показывает кандидатов, файлы/байты и причины сохранения; не создаёт запись выполнения, блокировку или отчёт. HARNESS CLEANUP APPLY под блокировкой состояния выполнения заново вычисляет кандидатов и повторно проверяет каждый каталог непосредственно перед удалением. Предыдущий CHECK не является разрешением.

Нужны подтверждённый владелец, успешное завершение всей команды/цепочки, а для STEP — доказательство завершения всего шага. Активные зависимости и ссылки из канонических документов сохраняют файлы. Незавершённый PLAN/IMPLEMENT, неизвестный владелец, утраченная запись истории, символическая ссылка, файл блокировки и недоступные документы не дают права удаления. Активное обновление блокирует APPLY.

Причины сохранения включают STEP_NOT_COMPLETE, OWNER_PROOF_MISSING, CANONICAL_REFERENCE, UNSAFE_LINK. Возраст не является основанием для удаления. Очистка не затрагивает каталоги execution, git, update-journal или verification-proofs; автоматическая уборка после успешной итоговой контрольной записи использует те же условия. Предупреждение уборки не отменяет основной SUCCESS; код завершения 2 означает предупреждение, а не разрешение удалить защищённые файлы.
