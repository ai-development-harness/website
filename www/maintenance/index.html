Поддержка и обновление

Как изменять живой проект без процессного долга: короткий путь для мелких правок, явное восстановление согласованности и безопасное обновление служебного слоя Harness.

Служебный слой Harness и код проекта обновляются по-разному

К Harness относятся AGENTS, runtime adapters, базовые навыки, протокол выполнения, docs/harness, политики, механизм обновления, валидатор и шаблоны. Проекту принадлежат REQ, ADR, архитектура, задачи, ревью, аудиты, код и тесты продукта, конфигурация и дополнительные навыки проекта или сторонних источников.

Для мелкой правки не нужен искусственный STEP

Опечатка, пунктуация, безопасный комментарий или локальное форматирование могут идти через QUICK FIX или ручную правку. Git diff и commit — достаточная история такой мелочи.

Короткий путь запрещён при изменении поведения, API, схемы или миграций, аутентификации и безопасности, зависимостей, архитектурных границ, существенной стратегии тестирования либо требований и критериев приёмки.

RECONCILE восстанавливает согласованность

Расхождения архитектуры, документации и статусов фиксируются явно. RECONCILE PROJECT создаёт отчёт аудита и корректирующий STEP там, где изменение нельзя безопасно спрятать в текущую задачу.

Обновление Harness — отдельный процесс

CHECK HARNESS UPDATE [TO <tag>]   # read-only route check
UPDATE HARNESS [TO <tag>]         # mutation того же target и route

Updater больше не рассматривает отдельный release tag как достаточное основание для перехода. Он читает canonical .project/harness-update-graph.json из configured source branch только как routing metadata, определяет конечный target и строит единственный допустимый маршрут от текущего lock release.

.project/harness.lock.json          → текущий BASE
.project/harness-update-graph.json  → latest + разрешённые переходы
.project/harness-update.toml        → ownership и merge rules каждого hop

Без TO <tag> конечный target берётся из harness-update-graph.json → latest. Явный TO фиксирует конкретный конечный target, но updater всё равно обязан доказать его достижимость. Затем весь route проверяется без записи и применяется строго hop-by-hop по immutable tags. Lock продвигается только после успешной postcondition-проверки конкретного hop.

Reload boundary. Если edge имеет reloadRequired: true, updater завершает текущий hop, фиксирует достигнутый release в lock и останавливается. После перезапуска runtime повторяется та же команда до исходного конечного target.

BASE / OURS / THEIRS и правила владения файлами

harness_owned

Локальное отличие от BASE блокирует скрытую перезапись.

shared

Для настраиваемых файлов выполняется трёхстороннее слияние. Сюда входят tracked role/config files Codex и Claude Code.

marker_merge

README и AGENTS объединяются с сохранением сгенерированных блоков проекта.

unknown

По умолчанию файл считается принадлежащим проекту, и механизм обновления его не меняет.

Старые проекты без lock требуют явного baseline

Если .project/harness.lock.json отсутствует, доказуемой BASE-версии нет. Harness не угадывает её по похожести файлов. Legacy adoption разрешён только когда известен конкретный неизменяемый release, которому соответствует исходное состояние Harness; при неизвестном baseline нужен ручной reconciliation.

Исторические исключения не являются частью постоянной инструкции. Обязательные промежуточные releases и reload boundaries задаются соответствующими edges в canonical .project/harness-update-graph.json, поэтому updater получает их из routing metadata, а не из захардкоженного сценария документации.

Граф и целевые релизы читаются как данные, а не исполняются

Moving source branch разрешено читать только для canonical .project/harness-update-graph.json. Сам граф содержит только routing metadata: latest, directed transitions, тип перехода и при необходимости reload boundary. Содержимое protocol layer каждого hop читается только из неизменяемых release tags. Скрипты миграции, установки и инициализации из графа или целевого релиза автоматически не запускаются.
