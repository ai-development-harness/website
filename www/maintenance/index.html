Поддержка и обновление

Как изменять живой проект без процессного долга: короткий путь для мелких правок, явное восстановление согласованности и безопасное обновление служебного слоя Harness.

Служебный слой Harness и код проекта обновляются по-разному

К Harness относятся AGENTS, адаптеры сред исполнения, базовые навыки, протокол выполнения, .harness/docs, политики, механизм обновления, валидатор и шаблоны. Проекту принадлежат REQ, ADR, архитектура, задачи, ревью, аудиты, код и тесты продукта, конфигурация и дополнительные навыки проекта или сторонних источников.

Для мелкой правки не нужен искусственный STEP

Опечатка, пунктуация, безопасный комментарий или локальное форматирование могут идти через PROJECT QUICK FIX или ручную правку. изменения Git и коммит — достаточная история такой мелочи.

Короткий путь запрещён при изменении поведения, API, схемы или миграций, аутентификации и безопасности, зависимостей, архитектурных границ, существенной стратегии тестирования либо требований и критериев приёмки.

PROJECT RECONCILE восстанавливает согласованность

Расхождения архитектуры, документации и статусов фиксируются явно. PROJECT RECONCILE создаёт отчёт аудита и корректирующий STEP там, где изменение нельзя безопасно спрятать в текущую задачу.

Обновление Harness — отдельный детерминированный процесс

HARNESS UPDATE CHECK [TO <tag>]   # проверка маршрута без изменений
HARNESS UPDATE APPLY [TO <tag>]   # применение того же целевого маршрута

# Эквивалентная цепочка:
HARNESS UPDATE CHECK [TO <tag>] > APPLY

проверить изменения
GIT CHECK > COMMIT > PUSH > PR

Обе команды обновления dispatcher направляет прямо в .harness/tools/harness-update.py без вызова модели. Агент не копирует файлы релиза вручную и не воспроизводит правила владения или слияния в рассуждениях. Механизм проверяет целостность текущего релиза, строит маршрут, моделирует конфликты и при APPLY выполняет файловую транзакцию.

.harness/harness.lock.json          → текущий BASE
.harness/harness-update-graph.json  → latest + разрешённые переходы
.harness/harness-update.toml        → правила владения и слияния каждого перехода

Без TO <tag> конечная версия берётся из поля latest; явный TO фиксирует target, но updater всё равно обязан доказать достижимый маршрут. Lock продвигается только после успешной postcondition каждого перехода.

Граница перезапуска. Если переход имеет reloadRequired: true, updater завершает текущий переход, фиксирует достигнутый релиз и возвращает машинное следующее действие. После перезапуска та же целевая команда продолжает маршрут уже новым кодом Harness.

BASE / OURS / THEIRS и правила владения файлами

harness_owned

Локальное отличие от BASE блокирует скрытую перезапись.

shared

Для настраиваемых файлов выполняется трёхстороннее слияние. Сюда входят отслеживаемые файлы ролей и конфигурации Codex и Claude Code.

marker_merge

README и AGENTS объединяются с сохранением сгенерированных блоков проекта.

unknown

По умолчанию файл считается принадлежащим проекту, и механизм обновления его не меняет.

Схема проектных документов мигрируется отдельно

HARNESS UPDATE APPLY обновляет служебный слой, но не переписывает активные проектные шаблоны REQ/ADR/OQ/STEP. Если целевой релиз требует миграции, валидатор оставляет явное состояние ожидания миграции; затем PROJECT RECONCILE идемпотентно обновляет активные документы и шаблоны и пересобирает проекции. Неизменяемые исторические отчёты остаются без изменений.

Поддерживаемая точка входа обновления начинается с v0.6.0

Текущий updater принимает проекты, синхронизированные с Harness v0.6.0 или новее. Более ранние переходы могут оставаться в графе как исторические данные и регрессионные сценарии, но не считаются поддерживаемой рабочей точкой входа.

Если .harness/harness.lock.json отсутствует, доказуемой BASE-версии нет. Harness не угадывает её по похожести файлов: для подключения нужен известный неизменяемый релиз в поддерживаемом диапазоне либо ручное восстановление согласованности.

Маршрут определяется данными. Обязательные промежуточные релизы и границы перезапуска задаются .harness/harness-update-graph.json, а не захардкоженным сценарием документации.

Изменяющие операции Git тоже проходят детерминированную предварительную проверку

Перед GIT CHECK, GIT COMMIT, GIT PUSH, GIT PR, GIT PR FINISH и GIT SYNC используется .harness/tools/git-preflight.py. Он возвращает PASS/BLOCKED и точный план изменяющей операции, но сам не делает коммит, отправку изменений или очистку ветки.

Для GIT PR FINISH предварительная проверка отдельно подтверждает, что PR уже имеет состояние MERGED, текущее рабочее дерево чистое, локальный HEAD соответствует GitHub headRefOid, а ветку возврата можно безопасно обновить в режиме fast-forward. Локальный .harness/local/git/pr-state.json удаляется только после полностью успешного завершения.

GitHub CLI — отдельная возможность, а не зависимость всего Git-процесса. Для GIT PR и GIT PR FINISH нужен установленный и авторизованный gh. GIT CHECK, GIT COMMIT, GIT PUSH и GIT SYNC используют обычный Git.

Граф и целевые релизы читаются как данные, а не исполняются

Изменяемую исходную ветку разрешено читать только для канонический .harness/harness-update-graph.json. Сам граф содержит только данные маршрутизации: latest, направленные переходы, тип перехода и при необходимости границу перезапуска. Содержимое служебного слоя протокола каждого перехода читается только из неизменяемых тегов релизов. Скрипты миграции, установки и инициализации из графа или целевого релиза автоматически не запускаются.
