Документация Harness

Начало работы

От пустого шаблона до базы знаний проекта и первого исполнимого STEP — с Codex или Claude Code и без создания кода продукта во время инициализации.

Что понадобится

Harness использует состояние Git, diff/index и Git-процесс как часть формальных проверок. Для штатного валидатора нужен Python 3.11+; это служебная зависимость Harness, а не зависимость самого приложения. Для выполнения команд нужен один поддерживаемый AI runtime: Codex или Claude Code.

Git

Нужен для контроля состояния репозитория, безопасных commit/push-операций и прослеживаемости изменений.

Python 3.11+

Нужен для tools/harness/validate.py, включая разбор TOML стандартным модулем tomllib.

Codex или Claude Code

Оба runtime поддерживаются отдельными adapter-конфигурациями поверх общего Harness protocol.

1. Создайте репозиторий из шаблона

Создайте новый репозиторий на основе официального шаблона AI Development Harness: открыть форму создания репозитория на GitHub. GitHub создаст отдельный репозиторий вашего проекта с готовой структурой Harness. После этого клонируйте уже свой созданный репозиторий.

Не удаляйте .project/harness.lock.json. Он хранит известную базовую версию Harness и нужен будущим CHECK HARNESS UPDATE / UPDATE HARNESS. Основой обновления служит неизменяемый тег релиза, а не постоянно меняющаяся ветка main.

2. Опишите проект своими словами

cp PROJECT_BRIEF.example.md PROJECT_BRIEF.local.md

Brief — локальное исходное описание проекта. Полезно указать цель, пользователей, сценарии, ограничения, обязательные или желательные технологии, то, что не входит в проект, и ссылки на примеры. Заранее оформлять REQ, ADR и STEP не требуется.

3. Откройте проект в Codex или Claude Code

Выберите тот runtime, которым хотите пользоваться. Harness protocol остаётся одним и тем же, а runtime-specific настройки уже лежат в репозитории.

Codex

.codex/config.toml регистрирует роли, а .codex/agents/*.toml задают model и reasoning effort для каждой роли.

Claude Code

CLAUDE.md импортирует @AGENTS.md; .claude/settings.json и .claude/agents/*.md задают root profile и роли.

Подробнее о runtime adapters →

4. Запустите INIT PROJECT

INIT PROJECT

Инициализатор читает brief и создаёт базу знаний проекта: docs/PROJECT.md, требования, базовую архитектуру, дорожную карту и полноценные STEP-NNN. Он связывает REQ ↔ ADR ↔ STEP и заполняет границы задачи, зависимости, критерии приёмки и проверки.

INIT PROJECT не создаёт код продукта. Инициализация заканчивается только после проверки согласованности и установки project.initialized: true.

5. Проверьте результат инициализации

Убедитесь, что требования не выдуманы, ADR не создаются «на всякий случай», зависимости не потеряны, а первые STEP действительно исполнимы.

STATUS PROJECT
NEXT STEP

6. Зафиксируйте основу

GIT CHECK
COMMIT
PUSH

Правила работы с Git находятся в .project/git-policy.toml. COMMIT и PUSH разделены: Harness не публикует изменения автоматически только потому, что реализация завершена.

7. Начните разработку

Можно выполнять этапы вручную или запускать весь допустимый цикл одной командой.

Ручной режим

PLAN STEP-001
IMPLEMENT STEP-001
REVIEW STEP-001

Автоматический режим

RUN STEP-001
Harness сам проходит допустимые стадии и останавливается при блокирующей проблеме.

Новая задача формулируется обычным языком через ADD STEP: <описание>.

8. Обновляйте Harness отдельно

CHECK HARNESS UPDATE
UPDATE HARNESS

Самообновление относится к служебному слою Harness, а не к работе над продуктом. Оно не создаёт STEP и не делает commit/push/PR автоматически. Shared-конфигурации Codex и Claude сохраняют проектные настройки через трёхстороннее слияние.
