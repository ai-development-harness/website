Документация Harness

Начало работы

От пустого шаблона до базы знаний проекта и первого исполнимого STEP — без создания кода продукта во время инициализации.

Что понадобится

Harness использует состояние Git, diff/index и Git-процесс как часть формальных проверок. Для штатного валидатора нужен Python 3.11+; это служебная зависимость Harness, а не зависимость самого приложения.

Git

Нужен для контроля состояния репозитория, безопасных commit/push-операций и прослеживаемости изменений.

Python 3.11+

Нужен для tools/harness/validate.py, включая разбор TOML стандартным модулем tomllib.

1. Создайте репозиторий из шаблона

Предпочтительный путь — GitHub Use this template. После этого клонируйте уже созданный репозиторий проекта.

Не удаляйте .project/harness.lock.json. Он хранит известную базовую версию Harness и нужен будущим CHECK HARNESS UPDATE / UPDATE HARNESS. Основой обновления служит неизменяемый тег релиза, а не постоянно меняющаяся ветка main.

2. Опишите проект своими словами

cp PROJECT_BRIEF.example.md PROJECT_BRIEF.local.md

Brief — локальное исходное описание проекта. Полезно указать цель, пользователей, сценарии, ограничения, обязательные или желательные технологии, то, что не входит в проект, и ссылки на примеры. Заранее оформлять REQ, ADR и STEP не требуется.

3. Запустите INIT PROJECT

INIT PROJECT

Инициализатор читает brief и создаёт базу знаний проекта: docs/PROJECT.md, требования, базовую архитектуру, дорожную карту и полноценные STEP-NNN. Он связывает REQ ↔ ADR ↔ STEP и заполняет границы задачи, зависимости, критерии приёмки и проверки.

INIT PROJECT не создаёт код продукта. Инициализация заканчивается только после проверки согласованности и установки project.initialized: true.

4. Проверьте результат инициализации

Убедитесь, что требования не выдуманы, ADR не создаются «на всякий случай», зависимости не потеряны, а первые STEP действительно исполнимы.

STATUS PROJECT
NEXT STEP

5. Зафиксируйте основу

GIT CHECK
COMMIT
PUSH

Правила работы с Git находятся в .project/git-policy.toml. COMMIT и PUSH разделены: Harness не публикует изменения автоматически только потому, что реализация завершена.

6. Начните разработку

Можно выполнять этапы вручную или запускать весь допустимый цикл одной командой.

Ручной режим

PLAN STEP-001
IMPLEMENT STEP-001
REVIEW STEP-001

Автоматический режим

RUN STEP-001
Harness сам проходит допустимые стадии и останавливается при блокирующей проблеме.

Новая задача формулируется обычным языком через ADD STEP: <описание>.

7. Обновляйте Harness отдельно

CHECK HARNESS UPDATE
UPDATE HARNESS

Самообновление относится к служебному слою Harness, а не к работе над продуктом. Оно не создаёт STEP и не делает commit/push/PR автоматически.
