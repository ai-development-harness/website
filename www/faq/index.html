Документация Harness

FAQ

Короткие ответы на вопросы, которые возникают перед первым запуском и во время долгой жизни проекта.

Частые вопросы

Harness — это фреймворк приложения?
Нет. Это repository-level process layer: правила, agents, skills, policies, templates и deterministic tooling. Product runtime выбирается и появляется после INIT/реальных STEP.
Нужно ли оформлять REQ и ADR вручную до INIT PROJECT?
Нет. PROJECT_BRIEF.local.md — сырой вход. Initializer нормализует требования и создаёт ADR только там, где устойчивое решение действительно принято или обязательно до реализации.
INIT PROJECT сразу пишет production code?
Нет. Bootstrap создаёт project knowledge base, architecture baseline, roadmap и task contracts. Production code во время INIT не создаётся.
Любая мелкая правка требует STEP?
Нет. Подтверждённый micro-change может идти через QUICK FIX или ручную правку → GIT CHECK → COMMIT. Behavior/API/data/security/architecture/dependency change требует ADD STEP.
Почему PLAN сохраняется в STEP?
Чтобы plan был durable handoff, а не памятью текущего чата. Implementer в новой сессии должен иметь достаточно контекста для работы без пересказа planner.
Почему REVIEW отдельным файлом?
Review report — исторический immutable artifact с verdict и findings. Исправления не должны стирать факт исходного review.
Можно ли продолжить проект в новой AI-сессии?
Это одна из основных целей Harness: контекст восстанавливается из repository artifacts — PROJECT, REQ, ADR, STEP, saved plan, code/tests, evidence и review reports.
Как обновлять Harness в уже идущем проекте?
Через CHECK HARNESS UPDATE, затем UPDATE HARNESS. Updater использует release lock, immutable tags и ownership policy; commit/push/PR выполняются отдельно после inspect diff.
Что произойдёт с моими настройками .codex при update?
Эти пути считаются shared: updater использует 3-way merge BASE/OURS/THEIRS и останавливается при конфликте вместо silent overwrite.
Что если проект старый и harness.lock.json отсутствует?
Это legacy-adoption case. Harness не угадывает BASE автоматически: нужен известный immutable release tag или ручной reconciliation.
Почему validator на Python?
Текущие проверки требуют структурного TOML parsing, Git index, path/glob semantics и UTF-8/binary handling. Python 3.11+ даёт standard-library tomllib; shell без дополнительных parsers сделал бы gate слабее.
Harness автоматически делает commit и push после реализации?
Нет. IMPLEMENT/REVIEW отделены от публикации. Git flow запускается явно: GIT CHECK → COMMIT → PUSH → PR согласно policy.

Куда дальше

Если вы только начинаете — откройте руководство по старту. Для точной семантики команд используйте справочник команд, а для update lifecycle — поддержку и обновление.
