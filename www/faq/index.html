Документация Harness

FAQ

Короткие ответы на вопросы, которые возникают перед первым запуском и во время долгой жизни проекта.

Частые вопросы

Harness — это фреймворк приложения?
Нет. Это слой процесса на уровне репозитория: правила, агенты, навыки, политики, шаблоны и формальные проверки. Технологии самого приложения выбираются и появляются после INIT и реальных STEP.
Какие AI runtime поддерживает Harness?
Codex и Claude Code. Они подключаются как отдельные runtime adapters к одному Harness protocol. AGENTS.md, команды, REQ/ADR/STEP, skills, Git policy и update policy остаются общими. Подробнее — на странице «Codex и Claude Code».
Нужно ли использовать Codex и Claude Code одновременно?
Нет. Для работы достаточно одного поддерживаемого runtime. Можно выбрать Codex или Claude Code в зависимости от текущей среды и при необходимости сменить runtime позже, не перенося проектный процесс в другой формат.
Нужно ли оформлять REQ и ADR вручную до INIT PROJECT?
Нет. PROJECT_BRIEF.local.md — исходное описание проекта. Инициализатор нормализует требования и создаёт ADR только там, где устойчивое решение действительно принято или необходимо до реализации.
INIT PROJECT сразу пишет код продукта?
Нет. Инициализация создаёт базу знаний проекта, базовую архитектуру, дорожную карту и контракты задач. Код продукта во время INIT не создаётся.
Любая мелкая правка требует STEP?
Нет. Подтверждённая небольшая правка с низким риском может идти через QUICK FIX или ручную правку → GIT CHECK → COMMIT. Изменение поведения, API, данных, безопасности, архитектуры или зависимостей требует ADD STEP.
Почему PLAN сохраняется в STEP?
Чтобы план был сохраняемым контекстом между этапами, а не памятью текущего чата. Реализатор в новой сессии должен получить достаточно информации без пересказа предыдущего разговора.
Почему REVIEW сохраняется отдельным файлом?
Отчёт ревью — неизменяемый исторический артефакт с итогом и замечаниями. Исправления не должны стирать факт исходной проверки.
Можно ли продолжить проект в новой AI-сессии?
Это одна из основных целей Harness: контекст восстанавливается из артефактов репозитория — PROJECT, REQ, ADR, STEP, сохранённого плана, кода и тестов, доказательств выполнения и отчётов ревью.
Как обновлять Harness в уже идущем проекте?
Через CHECK HARNESS UPDATE, затем UPDATE HARNESS. Lock фиксирует текущий BASE, canonical .project/harness-update-graph.json задаёт допустимый маршрут и конечный latest, а update policy определяет ownership/merge rules каждого hop. Весь маршрут сначала проверяется без записи, затем применяется hop-by-hop по неизменяемым release tags; commit/push/PR выполняются отдельно после проверки diff.
Что произойдёт с моими настройками Codex и Claude Code при обновлении?
.codex/config.toml, .codex/agents/*.toml, CLAUDE.md, .claude/settings.json и .claude/agents/*.md относятся к shared paths. Механизм обновления использует трёхстороннее слияние BASE/OURS/THEIRS и останавливается при конфликте вместо скрытой перезаписи проектных настроек.
Что если проект старый и harness.lock.json отсутствует?
Тогда требуется явное подключение старого проекта. Harness не угадывает BASE автоматически: нужен известный неизменяемый тег релиза или ручное восстановление согласованности.
Почему валидатор написан на Python?
Текущие проверки требуют структурного разбора TOML, работы с Git index, путями и glob-шаблонами, а также корректной обработки UTF-8 и бинарных файлов. Python 3.11+ даёт стандартный tomllib; shell без дополнительных парсеров сделал бы проверку слабее.
Harness автоматически делает commit и push после реализации?
Нет. IMPLEMENT/REVIEW отделены от публикации. Git-процесс запускается явно: GIT CHECK → COMMIT → PUSH → PR согласно правилам проекта.
