Документация Harness

Процесс разработки

Полный жизненный цикл AI-задачи: контракт задачи, сохранённый план, проверяемая реализация, независимое ревью и явная публикация в Git.

Каждый этап сохраняет контекст для следующего

История чата не является базой знаний. Каждая стадия сохраняет результат в репозитории: PLAN — в задаче, REVIEW — в неизменяемом отчёте, RECONCILE — в отчёте аудита, завершение — в доказательствах выполнения и представлениях состояния.

Доказательства должны оставаться проверяемыми. Буквально сохранённый вывод нельзя подменять пересказом. Если полный вывод не сохраняется, Harness фиксирует как минимум выполненную команду, код завершения и нормализованное наблюдение Observed с проверяемыми фактами.
Главная идея: следующая сессия должна продолжить работу из состояния репозитория, не требуя пересказа предыдущего разговора.

От запроса к контракту задачи

STEP ADD: <описание> проверяет дубликаты, выбирает стабильный ID, связывает REQ/ADR, вычисляет зависимости и формирует цель, контекст, границы изменений, правила изменения файлов, исключения, критерии приёмки, проверки и ожидаемые результаты.

Код продукта на этом этапе не меняется.

STEP RUN: автоматический цикл

STEP PLAN: contract check + independent planning review
  → STEP IMPLEMENT
  → deterministic verification
  → STEP REVIEW: immutable Review Contract v2
  → [условно security/test review]
  → STEP FIX ↔ STEP REVIEW
       ↳ NO_PROGRESS / REPEATED_FINDINGS / REGRESSION → BLOCKED
       ↳ hard cap execution.maxFixReviewCycles
  → CLOSE

Для обычных задач разработки переходы между PLAN, IMPLEMENT, REVIEW и FIX вычисляет диспетчер — без отдельного вызова модели на каждом переходе. Модель остаётся там, где нужна смысловая работа: подготовить план, изменить код, найти дефекты или исправить замечания. проверка запускается машинно, а доказательства фиксируются по фактическому результату команд.

Ревью с вердиктом FAIL передаёт FIX структурированные замечания Review Contract v2 с устойчивыми отпечатками. Следующие REVIEW сравниваются детерминированно: .harness/tools/repair_cycle.py может остановить цикл раньше абсолютного лимита при отсутствии прогресса, повторе тех же замечаний или доказанной регрессии. Изменение границ контракта отключает такое сравнение ради безопасности, а первый FAIL никогда не считается основанием для адаптивной остановки.

Специальные типы STEP могут использовать смысловую оркестрацию самого STEP RUN. Блокирующая проблема, детерминированная адаптивная остановка или исчерпание абсолютного лимита останавливают процесс: Harness не маскирует неуспешный результат.

Планируйте выбранную работу по требованию: STEP NEXT рекомендует STEP RUN STEP-NNN после проверки зависимостей. RUN перед IMPLEMENT обновляет отсутствующий или устаревший план и получает новый независимый отчёт проверки плана. Отдельный запуск STEP IMPLEMENT со старым Ready остаётся BLOCKED. Явный PLAN допустим заранее, но изменение REQ/ADR/архитектуры потребует повторного планирования; массово обновлять все будущие планы не нужно.

Для прерванной работы NEXT возвращает исходную корневую команду или цепочку; selected.nextChildCommand — диагностика, а не команда самостоятельного запуска. Если Ready-план содержит гипотезу, IMPLEMENT сначала ограниченно проверяет её: опровергнутый сценарий отбрасывается, подтверждённое новое изменение требует свежего PLAN. Это не разрешение расширять границы задачи.

Тот же процесс можно запускать вручную

STEP PLAN STEP-NNN сначала пытается доказать, что контракт задачи непротиворечив и исполним. Затем сохраняет план реализации и запускает независимую семантическую проверку плана. План считается готовым только при совпадающем PASS, актуальном context_basis и plan_content_hash.

STEP IMPLEMENT STEP-NNN работает только по готовому плану. STEP REVIEW STEP-NNN проверяет точную ревизию репозитория: дефект реализации даёт FAIL и ведёт в FIX, а противоречие контракта или отсутствующее архитектурное решение даёт BLOCKED и останавливает цикл.

Небольшая правка идёт по короткому пути

PROJECT QUICK FIX: исправь опечатку…
        ↓
proportional check
        ↓
GIT CHECK
        ↓
GIT COMMIT

PROJECT QUICK FIX допустим только без изменения поведения продукта, API, данных, безопасности, архитектуры и зависимостей. Если фактические границы правки шире — Harness останавливает короткий путь и предлагает STEP ADD:.

Расхождения не скрываются — согласованность восстанавливается явно

PROJECT RECONCILE сравнивает код, тесты и конфигурацию с REQ, ADR, архитектурой, STEP и доказательствами выполнения. Результат — отчёт аудита и при необходимости корректирующий STEP. Код продукта молча не переписывается.

Публикация отделена от реализации

GIT CHECK > COMMIT > PUSH > PR
        ↓ после слияния PR
GIT PR FINISH

STEP IMPLEMENT / STEP REVIEW сами не создают коммиты. GIT CHECK, GIT SYNC и GIT PR FINISH выполняются детерминированно; изменяющие операции проходят .harness/tools/git-preflight.py. Для GIT PUSH после доказанного GIT COMMIT в той же цепочке доступен машинный быстрый путь без повторной смысловой проверки модели.

GIT COMMIT фиксирует проверенный снимок ветки, родителя и дерева индекса, сверяет его прямо перед коммитом и проверяет фактические ветка/родитель/дерево после выполнения пользовательских хуков Git. Если проверенное состояние изменилось, команда возвращает COMMIT_POSTCONDITION_FAILED и компенсирует только доказанно принадлежащую ей изменение ref; разрушительный reset не используется.

Команды COMMIT/PUSH/PR сохраняют ограниченную контрольную запись внешней операции. После сбоя исполнитель сначала наблюдает внешний результат: уже применённая операция повторно учитывается, доказанно неизменившееся исходное состояние допускает безопасную повторную попытку, а неоднозначное состояние блокируется как SIDE_EFFECT_RECOVERY_AMBIGUOUS.

После успешного GIT PR Harness сохраняет локальное состояние Pull Request. Когда PR уже слит, GIT PR FINISH проверяет состояние MERGED, подтверждает точный head SHA, безопасно возвращает рабочую копию на исходную ветку и удаляет только проверенную локальную ветку PR. Это работает и после squash/rebase-слияния без git branch -D, reset или автоматического rebase.

Сервис Pull Request настраивается явно. GitHub использует пару github → gh, Gitea — gitea → tea. Обычные GIT CHECK, GIT COMMIT, GIT PUSH и GIT SYNC остаются независимыми от сервиса и используют обычный Git.

До реализации Harness проверяет качество самого контракта

Структурно корректного Markdown недостаточно. Перед реализацией Harness разделяет несколько вопросов, которые раньше легко смешивались в один «хороший план».

структурная проверка
        ↓
качество требований
        ↓
согласованность планирования
        ↓
архитектурная полнота
        ↓
реализация

Качество требований

Достаточно ли определены поведение, сценарии, данные, ошибки, нефункциональные требования и критерии приёмки? Существенная неоднозначность возвращает NEEDS_INPUT или BLOCKED.

Согласованность планирования

Не противоречат ли друг другу REQ, ADR, STEP, зависимости, границы задачи и критерии приёмки? Плохая постановка не передаётся реализатору как будто она уже истинна.

Принципы проекта

Применимые блокирующие PRN-NNN становятся инженерными ограничениями: план должен либо соблюдать принцип, либо содержать явное согласованное отклонение.

REVIEW PASS и завершение STEP — разные решения

STEP REVIEW отвечает на вопрос, есть ли существенный дефект в проверенной реализации. Проверка завершённости и согласованности отвечает на другой вопрос: выполнены ли все обязательства текущего STEP, связанных требований и готового плана.

Verification
    ↓
STEP REVIEW
    ↓ вердикт ревью PASS
Completion / Convergence
    ├─ PASS    → закрыть STEP
    ├─ FAIL    → STEP FIX
    └─ BLOCKED → остановить RUN

Результат проверки завершённости сохраняется в том же неизменяемом отчёте REVIEW. Поэтому успешное ревью реализации не может скрыть недоделанный критерий приёмки или обязательство REQ.

Изменение требований не оставляет старые планы «готовыми»

REQ, ADR, OQ, STEP и Принципы проекта могут эволюционировать. Harness использует один отпечаток контекста планирования и детерминированный анализ влияния, чтобы затронутые планы становились устаревшими без догадок модели.

REQ / ADR / OQ / PRN изменён
        ↓
контекст планирования изменился
        ↓
затронутый план = stale
        ↓
STEP RUN / IMPLEMENT блокируется
        ↓
STEP PLAN

.harness/tools/impact-analysis.py показывает конкретную причину устаревания и точное следующее действие. Несвязанные STEP не блокируются только потому, что изменился соседний артефакт.

Продолжение на другом компьютере

Локальное восстановление и перенос между клонами различаются. execution-status.json, блокировки, журнал обновления, идентификаторы сессий и локальные подтверждения проверок не переносятся через Git. Сначала HARNESS RESUME ищет однозначное локальное продолжение; повреждение или утрату старой контрольной записи нельзя обойти переносимым входом.

Для другого компьютера portable-handoff.py --write --step STEP-017 --json создаёт проверяемые факты STEP, отпечатки контракта/плана и идентичность состояния Git. Нужны in_progress, чистое дерево и сохранённые изменения продукта. Путь документа передачи определяется рядом с protocol.taskDirectory, например planning/handoffs/STEP-017.json. Публикуйте только документ передачи отдельным коммитом через GIT CHECK > COMMIT > PUSH.

На втором компьютере явно обновите ссылки через git fetch и git pull --ff-only. Единственный родительский коммит текущего HEAD коммита публикации должен совпадать с исходным коммитом, а единственный изменённый путь — с документом передачи. Любой последующий коммит делает снимок устаревшим. Нужен ровно один STEP со статусом in_progress, актуальный Ready-план и независимый отчёт проверки плана.

Только в новом клоне без локальной истории HARNESS RESUME может начать новый локальный STEP PLAN с новым executionId. Его завершение требует новой ревизии плана и нового независимого отчёта проверки плана. Чужие IMPLEMENT/REVIEW/FIX, PASS и внешние операции не повторяются автоматически. Перед приёмкой выполняются необходимые локальные проверки. Документ передачи не обеспечивает распределённую блокировку двух компьютеров.

Повторное ревью и актуальность проверок

Первый STEP REVIEW — полное независимое ревью объекта проверки. После успешного FIX режим fix_delta ограничен исходными замечаниями, точным набором исправлений и прямыми регрессиями. Снимок дерева Git до FIX включает подготовленные и неподготовленные к коммиту изменения и неигнорируемые неотслеживаемые файлы; локальный набор изменений связан с executionId, исходным отчётом и ревизией после FIX. Отпечатки сохраняют идентичность замечаний.

Новое замечание должно относиться к изменённому пути и иметь явное причинное объяснение fixDeltaCausality. Соседний код читается для понимания исправления; дефект неизменённого поведения оформляется отдельно. Обязательные проверки безопасности и тестов сохраняются. Устаревший набор изменений, утраченное дерево Git, повреждение состояния или набор изменений больше 1 MiB дают BLOCKED; полный повторный REVIEW допускается по явному запросу через HARNESS_REVIEW_FULL=1. Не запускайте Git GC между FIX и соответствующим REVIEW.

По умолчанию проверки выполняются полностью. Инкрементальный режим требует явной проектной карты verification.impactMap, полного исходного PASS и локального подтверждения происхождения. Независимый проверяющий плана проверяет полноту входных данных, зависимостей и покрытия критериев приёмки; Harness проверяет структуру и отпечатки, но не может доказать полноту произвольных зависимостей, заданных шаблонами путей.

Затронутые и зависящие от них проверки выполняются заново; незатронутые PASS используются только при доказанной неизменности входов. Изменение REQ/ADR/критериев приёмки/плана, карты, файла фиксации зависимостей, окружения или набора инструментов, неизвестный путь, утрата локального подтверждения и высокие риски возвращают полный прогон. Ручные и продуктовые наблюдения нужны заново для текущего объекта. verify-selected.py возвращает completionProof=false; только канонический инструмент записи выпускает новые доказательства результата PASS с происхождением результатов.

Доказательства связаны с точными байтами, контрактом и основой контекста; редактируемая строка PASS сама ничего не доказывает. Изменение входов во время записи даёт VERIFICATION_INPUTS_STALE, потеря локального подтверждения — VERIFICATION_PROOF_MISSING. Кэш краткого продолжения после MANUAL_REQUIRED — отдельный механизм с лимитом 30 минут и проверкой всех входов.

Дефект после REVIEW PASS

Дефект после REVIEW PASS фиксируется новым неизменяемым наблюдением через .harness/tools/late-defect.py: исходный доверенный PASS, буквальный критерий приёмки, исходные условия, действие, ожидаемый и наблюдаемый результаты, хэш воспроизведения и invalidatedChecks. Старый REVIEW и исторические доказательства не переписываются.

Для in_progress STEP при свежем PASS проверки с подтверждённым происхождением разрешён FIX только после проверенного наблюдения: единственным новым входом может быть файл воспроизведения, исключение которого восстанавливает исходный хэш. Изменение продукта, старых доказательств или второй новый файл блокируют переход. Для уже completed STEP создаётся отдельный корректирующий STEP через STEP ADD. После исправления нужны новые проверки и независимый REVIEW; текущая приёмка не выводится из прежнего PASS.
