Команды Harness

Стабильный человеко-машинный интерфейс: короткие команды запускают предсказуемые процессы на уровне репозитория и оставляют сохраняемые артефакты.

Обновление Harness

CHECK HARNESS UPDATE [TO <tag>]

Read-only проверка маршрута обновления. Текущий BASE берётся из .project/harness.lock.json, а допустимый маршрут — из canonical .project/harness-update-graph.json. Без TO конечный target берётся из поля latest; с TO <tag> используется указанный тег, но он всё равно должен быть достижим по графу. Проверка моделирует весь route hop-by-hop и не меняет рабочее дерево.

Цепочка выполнения
Lock BASE
Update graph route
Simulate hops
Merge / blocker analysis
Read-only report

UPDATE HARNESS [TO <tag>]

После успешной проверки для того же конечного target и того же route применяет заранее проверенную цепочку строго hop-by-hop. Каждый переход читает содержимое Harness из неизменяемых release tags, применяет ownership/3-way rules и продвигает lock только после успешной postcondition-проверки. Если переход требует перезапуска updater, команда останавливается на достигнутом release и продолжается после reload повторным запуском.

Цепочка выполнения
Successful CHECK
Hop-by-hop update
3-way / ownership rules
Postcondition + lock
GIT CHECK
COMMIT
Сам тег не определяет допустимость обновления. Нужен маршрут от текущего release до target в .project/harness-update-graph.json. Граф задаёт только routing metadata и не может запускать scripts/hooks или подменять immutable release content.
