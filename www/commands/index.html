Документация Harness

Команды Harness

Стабильный человеко-машинный интерфейс: короткие команды запускают предсказуемые процессы на уровне репозитория и оставляют сохраняемые артефакты.

Канонический синтаксис и цепочки

В Harness v0.6.0 команды используют форму DOMAIN ACTION [TARGET]. Внутри поддерживаемого домена соседние операции можно объединять оператором >; область и target наследуются только там, где это явно разрешено протоколом.

PROJECT INIT
STEP ADD: Добавить экспорт PDF
STEP PLAN STEP-024 > IMPLEMENT > REVIEW
GIT CHECK > COMMIT > PUSH > PR
HARNESS UPDATE CHECK TO <tag> > APPLY

До запуска runtime вся explicit chain нормализуется и проверяется по .harness/command-transitions.json через .harness/tools/validate-command.py. Отсутствующий edge означает INVALID_CHAIN и ноль выполненных сегментов. Runtime-preconditions проверяются уже после structural PASS и могут дать BLOCKED.

Цепочки не пересекают домены. Например, STEP RUN STEP-024 > GIT COMMIT не поддерживается: работа над STEP и публикация Git остаются отдельными executions.

Execution Status и восстановление после прерывания

Каждый запуск имеет root command и режим single, chain или orchestration. Текущее состояние хранится локально в .harness/local/execution/execution-status.json: running, complete или blocked отдельно от результата команды PASS, SUCCESS, FAIL или BLOCKED.

После interruption resolver может вернуть RESUME, NEXT, DONE, BLOCKED или NOT_FOUND. Это позволяет продолжить незавершённый STEP RUN, не восстанавливая ход прошлой сессии из чата.

Обновление Harness

HARNESS UPDATE CHECK [TO <tag>]

Read-only проверка deterministic update engine .harness/tools/harness-update.py: маршрут, ownership, BASE/OURS/THEIRS и коллизии вычисляются машинно. Текущий BASE берётся из .harness/harness.lock.json, а допустимый маршрут — из canonical .harness/harness-update-graph.json. Без TO конечный target берётся из поля latest; с TO <tag> используется указанный тег, но он всё равно должен быть достижим по графу. Проверка моделирует весь route hop-by-hop и не меняет рабочее дерево.

Цепочка выполнения
Lock BASE
Update graph route
Simulate hops
Merge / blocker analysis
Read-only report

HARNESS UPDATE APPLY [TO <tag>]

После успешной проверки для того же конечного target и того же route применяет заранее проверенную цепочку строго hop-by-hop. Каждый переход читает содержимое Harness из неизменяемых release tags, применяет ownership/3-way rules и продвигает lock только после успешной postcondition-проверки. Если переход требует перезапуска updater, команда останавливается на достигнутом release и продолжается после reload повторным запуском.

Цепочка выполнения
Successful CHECK
Hop-by-hop update
3-way / ownership rules
Postcondition + lock
GIT CHECK
GIT COMMIT
Сам тег не определяет допустимость обновления. Нужен маршрут от текущего release до target в .harness/harness-update-graph.json. Граф задаёт только routing metadata и не может запускать scripts/hooks или подменять immutable release content.
