Документация Harness

Команды Harness

Стабильный человеко-машинный интерфейс: короткие команды запускают предсказуемые процессы на уровне репозитория и оставляют сохраняемые артефакты.

Канонический синтаксис и цепочки

Команды Harness используют форму DOMAIN ACTION [TARGET]. Внутри одного домена соседние операции можно объединять оператором >; домен и целевой объект наследуются только там, где это явно разрешено протоколом.

PROJECT INIT
STEP ADD: Добавить экспорт PDF
STEP PLAN STEP-024 > IMPLEMENT > REVIEW
GIT CHECK > COMMIT > PUSH > PR
HARNESS UPDATE CHECK TO <tag> > APPLY

Обычный запуск канонической команды проходит через единую детерминированную границу .harness/tools/harness-dispatch.py. Диспетчер нормализует вход, проверяет всю цепочку по .harness/command-transitions.json, регистрирует состояние выполнения, применяет предусловия и затем либо вызывает машинный обработчик, либо передаёт модели точный смысловой навык и минимальный контекст. .harness/tools/validate-command.py остаётся отдельной диагностической проверкой без изменений. Отсутствующий переход означает INVALID_CHAIN: ни один сегмент не запускается; нарушенное предусловие возвращает BLOCKED.

Для команд с целью STEP можно вводить сокращение из трёх и более цифр: например, STEP RUN 024 нормализуется в STEP RUN STEP-024. Тот же реестр хранит краткое описание, стабильную ссылку на документацию и режим reasoning для каждой команды. Сгенерированная .harness/reasoning-boundaries.json показывает внешним инструментам, где модель обязательна, не нужна или зависит от сценария.

Цепочки не пересекают домены. Например, STEP RUN STEP-024 > GIT COMMIT не поддерживается: работа над STEP и публикация Git остаются отдельными запусками.

Команды PLAN и REVIEW проходят разные проверки качества

STEP ADD / STEP PLAN

качество требований проверяет, достаточно ли определён контракт; согласованность планирования — согласован ли он; применимые блокирующие PRN-NNN становятся обязательными инженерными ограничениями.

STEP REVIEW

Сначала проверяется реализация. Даже при вердикте ревью PASS STEP закрывается только после отдельной проверки завершённости и согласованности.

PROJECT STATUS

Сводка использует детерминированное состояние проекта, покрытие прослеживаемости и актуальность планов; клиенты не должны восстанавливать эти факты из текста Markdown.

Планируйте выбранную работу по требованию: STEP NEXT рекомендует STEP RUN STEP-NNN после проверки зависимостей. RUN перед IMPLEMENT обновляет отсутствующий или устаревший план и получает новый независимый отчёт проверки плана. Отдельный запуск STEP IMPLEMENT со старым Ready остаётся BLOCKED. Явный PLAN допустим заранее, но изменение REQ/ADR/архитектуры потребует повторного планирования; массово обновлять все будущие планы не нужно.

Для прерванной работы NEXT возвращает исходную корневую команду или цепочку; selected.nextChildCommand — диагностика, а не команда самостоятельного запуска. Если Ready-план содержит гипотезу, IMPLEMENT сначала ограниченно проверяет её: опровергнутый сценарий отбрасывается, подтверждённое новое изменение требует свежего PLAN. Это не разрешение расширять границы задачи.

STEP REVIEW STEP-NNN

Независимая модель проверяет задачу, реализацию и доказательства для точной ревизии репозитория. При FAIL Review Contract v2 требует машиночитаемые замечания с устойчивыми id/fingerprint, точным location, сценарием, expected/observed, влиянием, направлением исправления, ограничениями и доказательства. Детерминированный отбор заранее определяет обязательные проверки безопасности и тестов, а .harness/tools/semantic-writer.py фиксирует точную ревизию, основания проверок и неизменяемый отчёт. Неполное или некорректное замечание v2 отклоняется. Даже PASS закрывает STEP только при наличии требуемого для его типа доказательства завершения.

STEP FIX STEP-NNN

Исправляет подтверждённые замечания последнего применимого FAIL-отчёта либо проверенное наблюдение после REVIEW PASS для активного STEP. Состояние выполнения и восстановление после прерывания

Каждый запуск имеет корневую команду и режим single, chain или orchestration. Текущее состояние хранится локально в .harness/local/execution/execution-status.json, а все операции чтения, изменения и записи сериализуются через .harness/local/execution/execution-status.lock. Это предотвращает потерю состояния между параллельными сессиями и подагентами.

Текущий формат schemaVersion: 2 хранит полные записи только для активных или возобновляемых выполнений, отдельные stepRecovery подтверждения и ограниченное окно recentTerminals. Для команд, изменяющих состояние, активная запись также может содержать ограниченное подтверждение current.context.sideEffect: подтверждение одной попытки с фазами prepared → side_effect_started → side_effect_observed → postconditions_verified. После перезапуска исполнитель сначала наблюдает внешний факт и классифицирует его как ALREADY_APPLIED, SAFE_RETRY или AMBIGUOUS, поэтому коммит, отправка и PR не повторяются вслепую.

Завершённая история автоматически компактизируется вместо бесконечного роста файла, а миграция старого локального формата выполняется самим слоем выполнения — PROJECT RECONCILE здесь не участвует. HARNESS STATUS показывает незавершённые исполнения вместе с остальным состоянием проекта, а HARNESS RESUME безопасно продолжает единственное однозначно возобновляемое выполнение. Во время активного .harness/local/update-journal/ та же блокировка образует границу с самообновлением: новые канонические изменения состояния выполнения ждут завершения фиксации или отката обновления.

Основа намерения проверяет актуальность REQ/ADR/STEP/принципов и Ready-плана перед локальным продолжением. Контроль продвижения блокирует повторяющееся отсутствие продвижения, цикл или ухудшение фактами: EXECUTION_STAGNATION, EXECUTION_CYCLE, EXECUTION_DRIFT. Повторный HARNESS STATUS счётчики не увеличивает; диагностика направляет к STEP PLAN STEP-NNN, а не к слепому повторению IMPLEMENT.

Обновление Harness

HARNESS UPDATE CHECK [TO <tag>]

Диспетчер вызывает .harness/tools/harness-update.py без модели. CHECK строго без изменений: проверяет неизменяемую основу BASE и целевой релиз, владение путями, трёхстороннее слияние и конфликты установки.

Обновление выполняется напрямую к конечному релизу за одну транзакцию, без промежуточных APPLY. .harness/harness.lock.json фиксирует установленный BASE; без TO из .harness/harness-update-graph.json читается только latest. Явный TO <tag> выбирает неизменяемый релиз без чтения каталога. Новый механизм не строит маршрут по transitions.

HARNESS UPDATE APPLY [TO <tag>]

APPLY заново проверяет условия перед записью. Один журнал .harness/local/update-journal/ хранит резервную копию служебных файлов, файл состояния и локального состояния выполнения. Проверка установки сверяет байты и права доступа, синтаксис и обязательные служебные конфигурации. Код целевого релиза и полный валидатор проекта не запускаются. Один неизменяемый отчёт UPDATE-*.md появляется после PASS.

Сбой до фиксации транзакции вызывает откат. CHECK при незавершённом журнале возвращает UPDATE_JOURNAL_PENDING; следующий APPLY сначала выполняет восстановление. UPDATED уже означает конечный релиз. При reloadRequired=true перезапустите среду перед следующей рабочей командой; повторять APPLY для достижения целевого релиза не нужно.

Установка меняет служебный слой Harness и файл состояния. Код, REQ/ADR/STEP, REVIEW, доказательства и проектные шаблоны сохраняются как есть: их повреждение или устаревание не блокирует установку. Успешное обновление не означает миграцию продуктовых данных, приёмку STEP или успешную проверку проекта. PROJECT RECONCILE выполняется отдельно, когда требуется миграция проектных документов.

Операции Git

Все изменяющие операции Git проходят предварительную проверку. .harness/tools/git-preflight.py вычисляет PASS/BLOCKED и точный план операции; изменение выполняется только после PASS. Обычные GIT CHECK, GIT COMMIT, GIT PUSH и GIT SYNC требуют только Git. Для Pull Request Harness использует настроенную пару сервиса и инструмента: github → gh или gitea → tea; неизвестная или несовместимая пара блокируется при неопределённости.

GIT COMMIT / GIT COMMIT: <подсказка>

Создаёт локальный коммит по правилам Conventional Commits и git-policy, но не доверяет состоянию между предварительной проверкой и фактическим git commit. До валидатора фиксируется снимок ветки, родителя и дерева индекса; прямо перед коммитом он сверяется повторно, а после коммита проверяются фактические ветка/родитель/дерево. Пользовательские хуки Git выполняются штатно. Если хук изменил проверенное состояние, команда возвращает COMMIT_POSTCONDITION_FAILED и пытается компенсировать только доказанно принадлежащую этой операции изменение ref через reflog/CAS; разрушительный git reset --hard не используется.

Рабочие снимки, вспомогательные скрипты и промежуточные логи кладите в temporaryDirectory из документа передачи: .harness/local/tmp/<executionId>/. Доказательства, неизменяемые REVIEW и данные восстановления хранятся у своих владельцев вне tmp.

HARNESS CLEANUP CHECK только показывает кандидатов, файлы/байты и причины сохранения; не создаёт запись выполнения, блокировку или отчёт. HARNESS CLEANUP APPLY под блокировкой состояния выполнения заново вычисляет кандидатов и повторно проверяет каждый каталог непосредственно перед удалением. Предыдущий CHECK не является разрешением.

Нужны подтверждённый владелец, успешное завершение всей команды/цепочки, а для STEP — доказательство завершения всего шага. Активные зависимости и ссылки из канонических документов сохраняют файлы. Незавершённый PLAN/IMPLEMENT, неизвестный владелец, утраченная запись истории, символическая ссылка, файл блокировки и недоступные документы не дают права удаления. Активное обновление блокирует APPLY.

Причины сохранения включают STEP_NOT_COMPLETE, OWNER_PROOF_MISSING, CANONICAL_REFERENCE, UNSAFE_LINK. Возраст не является основанием для удаления. Очистка не затрагивает каталоги execution, git, update-journal или verification-proofs; автоматическая уборка после успешной итоговой контрольной записи использует те же условия. Предупреждение уборки не отменяет основной SUCCESS; код завершения 2 означает предупреждение, а не разрешение удалить защищённые файлы.

Продолжение на другом компьютере

Локальное восстановление и перенос между клонами различаются. execution-status.json, блокировки, журнал обновления, идентификаторы сессий и локальные подтверждения проверок не переносятся через Git. Сначала HARNESS RESUME ищет однозначное локальное продолжение; повреждение или утрату старой контрольной записи нельзя обойти переносимым входом.

Для другого компьютера portable-handoff.py --write --step STEP-017 --json создаёт проверяемые факты STEP, отпечатки контракта/плана и идентичность состояния Git. Нужны in_progress, чистое дерево и сохранённые изменения продукта. Путь документа передачи определяется рядом с protocol.taskDirectory, например planning/handoffs/STEP-017.json. Публикуйте только документ передачи отдельным коммитом через GIT CHECK > COMMIT > PUSH.

На втором компьютере явно обновите ссылки через git fetch и git pull --ff-only. Единственный родительский коммит текущего HEAD коммита публикации должен совпадать с исходным коммитом, а единственный изменённый путь — с документом передачи. Любой последующий коммит делает снимок устаревшим. Нужен ровно один STEP со статусом in_progress, актуальный Ready-план и независимый отчёт проверки плана.

Только в новом клоне без локальной истории HARNESS RESUME может начать новый локальный STEP PLAN с новым executionId. Его завершение требует новой ревизии плана и нового независимого отчёта проверки плана. Чужие IMPLEMENT/REVIEW/FIX, PASS и внешние операции не повторяются автоматически. Перед приёмкой выполняются необходимые локальные проверки. Документ передачи не обеспечивает распределённую блокировку двух компьютеров.

Повторное ревью и актуальность проверок

Первый STEP REVIEW — полное независимое ревью объекта проверки. После успешного FIX режим fix_delta ограничен исходными замечаниями, точным набором исправлений и прямыми регрессиями. Снимок дерева Git до FIX включает подготовленные и неподготовленные к коммиту изменения и неигнорируемые неотслеживаемые файлы; локальный набор изменений связан с executionId, исходным отчётом и ревизией после FIX. Отпечатки сохраняют идентичность замечаний.

Новое замечание должно относиться к изменённому пути и иметь явное причинное объяснение fixDeltaCausality. Соседний код читается для понимания исправления; дефект неизменённого поведения оформляется отдельно. Обязательные проверки безопасности и тестов сохраняются. Устаревший набор изменений, утраченное дерево Git, повреждение состояния или набор изменений больше 1 MiB дают BLOCKED; полный повторный REVIEW допускается по явному запросу через HARNESS_REVIEW_FULL=1. Не запускайте Git GC между FIX и соответствующим REVIEW.

По умолчанию проверки выполняются полностью. Инкрементальный режим требует явной проектной карты verification.impactMap, полного исходного PASS и локального подтверждения происхождения. Независимый проверяющий плана проверяет полноту входных данных, зависимостей и покрытия критериев приёмки; Harness проверяет структуру и отпечатки, но не может доказать полноту произвольных зависимостей, заданных шаблонами путей.

Затронутые и зависящие от них проверки выполняются заново; незатронутые PASS используются только при доказанной неизменности входов. Изменение REQ/ADR/критериев приёмки/плана, карты, файла фиксации зависимостей, окружения или набора инструментов, неизвестный путь, утрата локального подтверждения и высокие риски возвращают полный прогон. Ручные и продуктовые наблюдения нужны заново для текущего объекта. verify-selected.py возвращает completionProof=false; только канонический инструмент записи выпускает новые доказательства результата PASS с происхождением результатов.

Доказательства связаны с точными байтами, контрактом и основой контекста; редактируемая строка PASS сама ничего не доказывает. Изменение входов во время записи даёт VERIFICATION_INPUTS_STALE, потеря локального подтверждения — VERIFICATION_PROOF_MISSING. Кэш краткого продолжения после MANUAL_REQUIRED — отдельный механизм с лимитом 30 минут и проверкой всех входов.
