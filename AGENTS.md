# Инструкции для AI-агентов

Этот файл содержит проектные правила, которые обязательны для любых следующих AI-сессий при изменении сайта AI Development Harness.

## Структура статических ассетов

- JavaScript-файлы сайта хранятся только в `www/js/`.
- CSS-файлы сайта хранятся только в `www/css/`.
- Не создавать и не оставлять дубликаты `*.js` и `*.css` в корне `www/`.
- При переносе или переименовании ассета обязательно удалить старый файл и проверить, что старый путь больше нигде не используется.
- Изображения и другие графические ассеты хранятся в `www/assets/`.

## Cache busting для JS и CSS

Сайт статический и не использует bundler, поэтому версионирование ассетов выполняется явно через query-параметр `?v=`.

Правила:

1. Все локальные подключения JS и CSS должны содержать параметр вида `?v=<revision>`.
2. Используется один общий случайный revision-токен для текущей версии клиентских ассетов, например `?v=7f3c9a21`.
3. После **любого изменения любого файла в `www/js/` или `www/css/`** необходимо сгенерировать новый revision-токен и заменить старый токен:
   - во всех HTML-страницах сайта;
   - во всех динамических `import()` JS-модулей;
   - во всех динамически создаваемых `<link rel="stylesheet">`.
4. Один и тот же revision должен использоваться для всех локальных JS/CSS-подключений в рамках одного состояния репозитория.
5. Нельзя обновлять `?v=` только на одной странице: изменение должно применяться ко всем публичным HTML-страницам.
6. После изменения ассетов запустить тесты инфраструктурных инвариантов. CI должен падать при старых путях, отсутствующем `?v=` или разных revision-токенах.

Это правило заменяет автоматический content hashing, который обычно выполняет bundler вроде webpack/Vite.

## JavaScript

- Клиентские JS-скрипты сайта комментировать подробно на русском языке.
- Комментарии должны объяснять не только *что* делает блок, но и зачем выбран такой подход, если решение неочевидно.
- Не смешивать крупные независимые подсистемы в одном файле: поиск, тема и другие значимые функции должны быть вынесены по смыслу.

## Пакетный менеджер

- Использовать только Yarn 1.22.22.
- Не добавлять `package-lock.json` и не использовать `npm install` / `npm ci` в документации, scripts или CI.

## Тесты

- Названия `test(...)` и `test.describe(...)` писать по-русски.
- Сам JavaScript-код тестов писать на английском: имена переменных, функций, helpers и локальных идентификаторов должны быть английскими.
- Русский язык внутри кода тестов использовать только в названиях suite/case, проверяемом пользовательском тексте и поясняющих сообщениях assertion, когда это действительно нужно.
- Тесты раскладывать по смысловым каталогам и файлам; не собирать независимые области в один большой spec.
- При изменении поведения добавлять регрессионные тесты, а не ограничиваться ручной проверкой.
